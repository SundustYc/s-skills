# 改写示例

> 本文件是解释和示例；行为规则以 `SKILL.md` 为准，两处不一致时按 `SKILL.md`。

每个示例给原文、改后、改了什么、不该改的点。示例文本均为合成。章节按 `SKILL.md` 六类问题排；标签错位通常和生造标签同时出现，并入第一节。第四节「不必要的术语」和第五节「没问过的对立项」是 agent 自己输出时最常犯的两类，例子也按 agent 回复的语境写。

## 一、生造词与标签（含标签错位）

### 示例 1：比喻式标签，且只概括前提

**原文**

> **缓存是系统的稳定器**：本地 LRU 能挡住大部分重复请求，但热点 key 过期瞬间会同时打到数据库，因此需要给热点 key 的 TTL 加随机抖动。

**改后**

> **本地缓存可用，但热点 key 要加 TTL 抖动**：本地 LRU 能挡住大部分重复请求，但热点 key 过期瞬间会同时打到数据库，因此需要给热点 key 的 TTL 加随机抖动。

**改了什么**

- "稳定器"在下文没有对应物，是比喻式生造。
- 标签只说了前提（缓存有用），正文结论是"加 TTL 抖动"，标签错位。
- 只改标签，正文一字不动。

**不该改的点**

- `LRU`、`TTL`、`热点 key` 是通行术语，保留。

### 示例 2：设计文档小节标题

**原文**

> ## 数据面的韧性设计
>
> 网关到后端的连接池上限 200，超过后新请求排队最多 50ms，再超直接返回 503。后端单实例故障时，健康检查 3 次失败后摘除，30 秒后重新探测。

**改后**

> ## 连接池限流与故障实例摘除
>
> 网关到后端的连接池上限 200，超过后新请求排队最多 50ms，再超直接返回 503。后端单实例故障时，健康检查 3 次失败后摘除，30 秒后重新探测。

**改了什么**

- "韧性设计"是抽象名词堆叠。读者看标题不知道这节讲连接池还是重试还是多活，无法决定跳不跳。
- 正文两件事：限流、摘除故障实例。标题直接写这两件事。

**不该改的点**

- 正文已经是直写，数字和条件全部保留。

### 示例 3：README 功能列表里的临时组合词

**原文**

> - 语义锚点机制：保证多轮对话中的指代一致
> - 增量式上下文对齐：只把变化的部分发给模型
> - 支持流式输出

"语义锚点""上下文对齐"在 README 全文只出现这一次，没有定义。

**改后**

> - 多轮对话中指代保持一致
> - 只把变化的部分发给模型，不重发整个上下文
> - 支持流式输出

**改了什么**

- 冒号前的名字是临时组合词，冒号后的解释才是内容。删掉名字，直接写内容。
- 第三条本来就是直写，不动。

**不该改的点**

- 如果这两个词在文档其他地方有定义并反复使用（例如配置项就叫 `semantic_anchor`），那它们是项目术语，保留并在第一次出现时给定义。

### 示例 4：未展开的内部缩写

**原文**（对外的接入文档）

> 商户回调由 DSM 统一下发，失败后进 RQ，由 OMS 兜底补偿。

全文没有一处展开这三个缩写，也没有缩写表。

**改后**

> 商户回调由下发服务（DSM）统一下发，失败后进重试队列（RQ），由订单管理系统（OMS）兜底补偿。

**改了什么**

- 三个缩写都是项目内部的，目标读者是外部商户，一律算未展开。
- 首次出现处展开，括号保留缩写，后文可以继续用缩写。
- 展开的全称来自项目代码和内部文档。**查不到全称时写 `DSM（全称待补）`，不编。**

**不该改的点**

- 如果这是给团队内部看的文档，且团队术语表已收录这三个缩写，不改。

### 示例 5：英文标题

**原文**

> ## Resilience Layer
>
> Requests to the backend go through a connection pool capped at 200. Excess requests wait up to 50 ms, then get a 503. An instance is removed after three failed health checks and re-probed after 30 s.

**改后**

> ## Connection pool limits and unhealthy-instance removal
>
> Requests to the backend go through a connection pool capped at 200. Excess requests wait up to 50 ms, then get a 503. An instance is removed after three failed health checks and re-probed after 30 s.

**改了什么**

- 和示例 2 是同一个问题换了语言。`Resilience Layer` 是抽象名词堆叠，正文里没有叫这个名字的组件。
- 标题改成正文的两件事。正文不动。

### 示例 5b：agent 给自己刚做的事起名

**语境**：用户问"表格解析那块你怎么改的"。

**原文**（agent 回复）

> 我把解析器改成了 schema-first 的 exact-head 检查：先做一轮 header-aware 的列对齐，再走 editorial-row 布局兜底。

**改后**

> 我把解析器改成先看表头再看内容：先用第一行的列名确定每列是什么，对不上的行按人工排版的表格处理。

**改了什么**

- `schema-first`、`exact-head 检查`、`header-aware`、`editorial-row 布局` 都是这一次回复里临时起的名字，用户没法查，下文也没有定义。每个都换成它指的动作。
- `兜底` → 写备用方案是什么。

**不该改的点**

- 如果代码里真有一个函数叫 `exactHeadCheck`，写 `exactHeadCheck`（先看表头再看内容）——代码标识符按字面保留，后面跟一句它做什么。

## 二、占用既有词

### 示例 6：借术语当形容词

**原文**

> 这个写入是原子的，单次只要 2ms。

上下文：前后文都在讨论写入延迟，没有任何地方提到部分写入、事务或回滚。

**改后**

> 这个写入单次只要 2ms。

**改了什么**

- "原子"的固定含义是"要么全生效、要么全不生效"，这句想说的是"快"。把定义代入句子——"这个写入要么全生效要么全不生效，单次只要 2ms"——前半句和后半句没关系，说明是占用。
- 上下文能确认作者在说速度，所以删掉，保留数字。

**不该改的点**

- 如果上下文能确认作者确实在说原子性（比如前文讨论部分写入失败的问题），那这句是两个独立事实，都保留，最多拆成两句。
- **上下文两头都说不通、判断不了时，不删。**保留原句并标注：`这个写入是原子的（"原子"指事务原子性还是速度？待确认），单次只要 2ms。` 删掉一个声称等于改动事实，宁可多一个待确认。

### 示例 7：混用"幂等"

**原文**

> 查询接口做了幂等处理，同样的参数第二次请求会直接返回缓存结果。

**改后**

> 查询接口加了结果缓存，同样的参数第二次请求直接返回缓存结果。

**改了什么**

- 幂等指"同一请求执行多次和一次结果相同"，查询接口天然幂等，这里说的是缓存。用了术语反而让读者去想"查询为什么需要幂等处理"。
- 前半句换成后半句已经说了的事：缓存。后半句"直接返回缓存结果"按字面保留，不改成"上次的结果"——缓存被淘汰后不一定是上次的，改了就是改事实。

## 三、抽象词代替机制

### 示例 8：上下文里查得到机制

**原文**

> 写入路径采用乐观并发的协调策略，失败时进入指数退避的韧性恢复流程。

查代码后确认：写入不加锁，提交时校验版本号，版本号不匹配则拒绝写入；被拒绝的写入按 1s、2s、4s 重试三次。

**改后**

> 写入用乐观并发：不加锁，提交时校验版本号，不匹配则拒绝并重试；重试按指数退避，间隔 1s、2s、4s，最多 3 次。

**改了什么**

- 原句复述测试不通过：说不出写入怎么做、失败后做什么。
- "协调策略""韧性恢复流程"都是抽象名词堆叠，从代码里查到具体行为后直写。
- `乐观并发`、`指数退避` 是通行术语，保留，机制紧跟在后面。术语给懂的读者压缩，机制给不懂的读者解码，两边都不吃亏。

**不该改的点**

- 如果上下文查不到细节，保留两个术语、只删堆叠的部分：`写入用乐观并发，失败后指数退避重试`。这已经比原句能复述，不用为了"更具体"编数字。

### 示例 9：上下文里查不到机制

**原文**

> 任务调度器具备智能的负载感知能力，能够自适应地把任务分配到合适的节点。

没有代码、配置或其他段落说明"智能""自适应"指什么。

**改后**

> 任务调度器按节点负载分配任务（分配规则待补）。

**改了什么**

- "智能""自适应""合适的"都是形容词替代机制。
- 原文实际声称的只有一件事：分配时看负载。压回这个范围，标注缺口。
- 没有替作者编一个规则，比如"分配到 CPU 最低的节点"。原文没说，不能补。

### 示例 10：研究笔记里的抽象替代

**原文**

> 该方法通过引入结构化先验，在表征层面实现了对下游任务的解耦，从而带来了泛化性能的提升。

原论文的具体做法：在编码器后加一个可学习的投影层，训练时对不同任务用不同的投影头。

**改后**

> 该方法在编码器后加一个可学习的投影层，不同下游任务用不同的投影头，泛化性能有提升。

**改了什么**

- "结构化先验""表征层面的解耦"复述不出做了什么，从原论文查到机制后直写。
- "泛化性能的提升"保留了，因为它是原文声称的结果；没有补数字，原文这句没给。

**不该改的点**

- `编码器`、`投影层`、`下游任务`、`泛化` 是通行术语。

### 示例 11：英文行文

**原文**

> The gateway leverages an adaptive orchestration strategy to intelligently route traffic.

上下文查不到路由规则。

**改后**

> The gateway routes traffic (routing rules to be documented).

**改了什么**

- `adaptive orchestration strategy`、`intelligently` 是形容词和名词短语代替机制，复述不出按什么路由。
- 压回原文实际声称的范围（网关做路由），标缺口。没有替作者编 "by latency" 或 "by region"。

## 四、不必要的术语

### 示例 12：agent 解释自己的改动

**语境**：用户问"你刚才改了什么"。用户是这个项目的开发者，但没参与这段逻辑。

**原文**（agent 回复）

> 我在入口处加了一层门控，对请求体做哈希后与缓存比对，命中则短路返回，未命中则走完整链路并落盘，形成闭环。返回结构遵循统一的响应合同。

**改后**

> 我在入口处加了一步检查：对请求体算哈希，和缓存里存的比对。比对上了直接返回缓存结果；比对不上就照原来的流程处理，处理完把结果写进缓存。返回格式和其他接口保持一致。

**改了什么**

- `门控` → "加了一步检查"。这里门控实际做的就是检查，读者要的是"检查什么、结果如何"。
- `短路返回`、`完整链路`、`落盘` → 各写实际动作。
- `形成闭环` → 删。它没有额外信息，"处理完写进缓存"已经是完整的一圈。
- `响应合同` → "返回格式"。

**不该改的点**

- `哈希` 保留。这里就是在算哈希，是本义，没有更直白的等价说法；换成"算成一个短标识"反而丢了信息。
- 如果这段是写进面向后端同事的设计文档，`落盘` 是压缩，可以留；`门控`、`闭环`、`合同` 仍然是不必要的。

### 示例 13：术语确实需要，补一句解释

**语境**：agent 向产品经理解释为什么重试是安全的。

**原文**

> 这个接口是幂等的，所以客户端重试不会有问题。

**改后**

> 这个接口重复调用多少次，结果都和调用一次一样（术语叫幂等），所以客户端重试不会重复扣款。

**改了什么**

- 目标读者不是工程师，"幂等"要多转一道弯。但这里"重复调用结果相同"正是论证的核心，去掉术语后信息没丢，所以先写直白说法。
- 术语放在括号里保留，因为后面和工程师沟通时要用同一个词，让产品经理知道对应关系。
- "不会有问题"换成上下文里实际担心的事（重复扣款）——这是第 4 类抽象词代替机制，顺手改掉。如果上下文没说担心什么，保留"不会有问题"，不编。

**不该改的点**

- 同一句话写给后端同事，直接用"幂等"，不解释。

### 示例 14：提交说明

**原文**

> refactor: 抽取校验原语，统一编排入口，收敛配置语义

**改后**

> refactor: 把三处重复的参数校验抽成一个函数，入口统一从 main 调用，配置项名称改成一致的

**改了什么**

- `校验原语` → "参数校验函数"。它就是一个函数。
- `统一编排入口` → 写实际做的事："入口统一从 main 调用"。
- `收敛配置语义` → 从 diff 里看实际改的是配置项命名，直接写。

**不该改的点**

- 改后的内容全部来自 diff。diff 里看不出"收敛配置语义"具体指什么时，写 `配置项调整（具体见 diff）`，不编。

### 示例 15：面向同行的技术文档，不改

**原文**（存储团队内部的设计文档）

> 写入先落盘再返回 ack；按 key 哈希分到 16 个 bucket，bucket 内保序。

**处理**：不改。

目标读者是存储团队，`落盘`、`哈希`、`ack`、`bucket` 都是他们每天用的压缩。换成直白说法会让句子变长且失去精确性（"写到磁盘"丢了持久化语义）。这一节的判据是"这个读者要不要多转一道弯"。

## 五、没问过的对立项

### 示例 16：agent 解释原因

**语境**：用户说"这个接口怎么一直超时"。

**原文**（agent 回复）

> 这不是网络问题，也不是数据库慢，而是配置里把 `read_timeout` 设成了 0，客户端一发请求就立刻放弃。

**改后**

> 配置里把 `read_timeout` 设成了 0，客户端一发请求就立刻放弃。

**改了什么**

- 用户没提网络，也没提数据库。两个被否定的项都是 agent 自己立的，读者要先接住两个候选再看到真正的原因。删掉，只留原因。

**不该改的点**

- 如果用户问的是"是不是网络问题"，回答 `不是网络问题，是配置里 read_timeout 设成了 0` 就是在回应用户的猜测，保留。
- 如果排查过程要交代（用户问"你怎么确定的"），"网络和数据库都查过，正常"是排查记录，放在原因后面单独说，也保留。

### 示例 17：agent 汇报改动

**语境**：用户说"把重试次数改成 5"。

**原文**（agent 回复）

> 已把 `max_retries` 从 3 改成 5。没有动重试间隔，也没有改超时配置，其他调用方不受影响。

**改后**

> 已把 `max_retries` 从 3 改成 5。

**改了什么**

- 用户只要求改一个值，没问间隔、超时、其他调用方。三条"没有动"都在回答没人问的问题。

**不该改的点**

- 如果 `max_retries` 和重试间隔在同一个配置块里，读者看到改动很可能以为间隔也一起动了，那么"重试间隔没动"是在排除一个真会有的误解，保留这一条。
- 用户问"还改了别的吗"，就照实列范围。

### 示例 18：英文

**原文**

> The fix isn't about the parser—it's about how the tokenizer handles trailing commas. This isn't a refactor; it's a two-line change.

上下文：用户报了一个 bug，没有提 parser，也没有提 refactor。

**改后**

> The tokenizer mishandled trailing commas. The fix is two lines.

**改了什么**

- `isn't about the parser`、`isn't a refactor` 都是没人提过的项。删掉后剩下的两句就是全部信息。

## 六、标注模式示例

用户说"先别改，标一下这段哪里看不懂"。

**原文**

> **可观测性底座**：所有服务统一接入 OpenTelemetry，trace 采样率 10%，日志经 Fluent Bit 收到 Loki。告警走 Alertmanager，按 SLO 燃尽速率触发。这一层为上层的智能诊断能力提供了数据基础。

**输出**

1. `问题类型`：生造词与标签 + 标签错位
   `触发点`：**可观测性底座**
   `读者会卡在哪`："底座"在下文没有对应物；正文是四条具体接入方式，标签只给了一个比喻。
   `建议动作`：改标签对齐结论，例如"统一接入 OTel、Loki 和 SLO 告警"。

2. `问题类型`：抽象词代替机制
   `触发点`：为上层的智能诊断能力提供了数据基础
   `读者会卡在哪`："智能诊断能力"是什么、在哪一层、用了这里的哪些数据，全文没有说。
   `建议动作`：如果文档其他地方有这个诊断模块，写它的名字和用到的数据；没有就删掉这句，或标缺口。

其余句子（OpenTelemetry、采样率、Fluent Bit、Loki、Alertmanager、SLO 燃尽速率）都是通行术语和具体配置，保持不动。

**这个输出没有做的事**

- 没有给整段改写稿。
- 没有把 `SLO 燃尽速率` 这类术语当作生造。

### 无问题时的输出

原文：

> 上线后发现慢查询，原因是新加的过滤条件没走索引。加了联合索引，p99 从 1.2s 降到 80ms。

输出只有一行：

> 未发现生造词、标签错位、占用、抽象替代、不必要的术语或没问过的对立项，建议保持不动。

不列空条目，不为了凑数硬找。
